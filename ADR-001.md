# ADR-001: Arquitectura de testing de TaskFlow

- **Estado:** Aceptada
- **Fecha:** 2026-09-22

## Contexto

TaskFlow cuenta actualmente con pruebas de API escritas con Jest y Supertest en `server/tests/`. Estas pruebas utilizan helpers para registrar usuarios y crear proyectos y tareas, además de una base SQLite independiente por archivo de prueba.

El framework de Playwright todavía no está implementado. Por lo tanto, actualmente no existen Page Objects, Component Objects ni fixtures de Playwright. La aplicación sí dispone de pantallas y atributos `data-testid` que permiten incorporar estos patrones.

## Decisión

Se utilizará Playwright con TypeScript y una arquitectura por capas que combine los siguientes patrones:

| Patrón | Dónde se utilizará | Por qué conviene en TaskFlow |
|---|---|---|
| **Page Object Model (POM)** | `LoginPage`, `ProjectsPage`, `BoardPage`, `TaskDetailPage` y `MembersPage` | Cada pantalla tiene acciones propias. POM permite centralizar sus locators y mantener los tests legibles. |
| **Fixtures** | Autenticación, creación de usuarios/proyectos y limpieza de datos | Varios tests necesitan el mismo estado inicial. Los fixtures evitan repetir el setup y garantizan la limpieza aunque una prueba falle. |
| **Component Object Model (COM)** | Componentes repetidos de la interfaz | Conviene cuando una pieza aparece varias veces y tiene locators o acciones propias. Evita duplicarlos en los Page Objects y en los tests. |
| **Patrón híbrido API + UI** | Preparación de datos por API y validación del comportamiento por UI | Crear las precondiciones por API es más rápido y estable que repetirlas mediante la interfaz. Playwright se usa en la UI solamente para validar el comportamiento relevante. |

Las pruebas existentes de Jest y Supertest se conservarán porque proporcionan feedback rápido sobre la API. Playwright agregará cobertura de interfaz y de flujos completos sin reemplazar esa suite.

## Cambio propuesto

Se propone crear `TaskCard` como primer Component Object.

Actualmente, `BoardPage.tsx` contiene directamente la tarjeta de tarea y la repite en las columnas `TODO`, `IN_PROGRESS` y `DONE`. La tarjeta incluye título, prioridad, responsable, vencimiento, cantidad de comentarios y cambio de estado.

`BoardPage` representará la pantalla completa, mientras que `TaskCard` encapsulará únicamente esa pieza repetida. El componente podrá exponer acciones como:

- consultar sus datos;
- abrir el detalle de la tarea;
- cambiar su estado.

Este cambio se justifica porque la tarjeta se repite, tiene comportamiento propio y ya cuenta con `data-testid` estables. Encapsularla reduce la duplicación sin introducir un patrón más complejo, como Screenplay, que no se justifica para el tamaño actual del proyecto.

## Consecuencias

- Los tests serán más legibles y tendrán menos locators duplicados.
- Los cambios de una pantalla se resolverán en su Page Object.
- Los cambios de las tarjetas se resolverán únicamente en `TaskCard`.
- Los fixtures permitirán ejecutar pruebas independientes y en paralelo.
- La preparación por API reducirá la duración de los escenarios de UI.
- Será necesario mantener los Page Objects, Component Objects y fixtures a medida que cambie la aplicación.
